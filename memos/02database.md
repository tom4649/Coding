## 1. リレーショナルデータベース（RDB）

データを「テーブル（表）」という構造で管理し、複数のテーブル間をリレーション（関連性）で結ぶデータベースである。何十年もの間、基幹システムを中心に主流であり続けている。

* **構造:** 行（レコード）と列（カラム）で構成される。事前に厳格なデータ構造（スキーマ）を定義する必要がある。
* **操作言語:** SQL（Structured Query Language）
* **強み:**
    * データの整合性と一貫性が極めて高い。「間違いが絶対に許されないデータ」（銀行の残高、決済処理、注文履歴など）の管理に適している。
    * 複雑な条件での結合（JOIN）や集計処理が強力である。
* **弱み:**
    * 大量データや超高アクセス（大量の書き込みなど）に対して、サーバーを複数台に分散（水平スケーリング）して性能を上げることが構造上難しい。
         * RDBは、データの処理を「トランザクション」という単位で管理し、ACID特性と呼ばれる厳格なルールを守るよう設計されているため、サーバー間での同期や確認の通信が大変。
         * データが複数台のサーバーに分散しているとJOINが大変。
         * CAPの定理: 「一貫性（C）」「可用性（A）」「分断耐性（P）」の3つのうち、同時に2つしか満たせない。RDは「一貫性（C）」と「可用性（A）」。NoSQLが選ぶのは「可用性（A）」と「分断耐性（P）」。
* **主要なプロダクト:** MySQL, PostgreSQL, Oracle Database, SQL Server

## 2. 非リレーショナルデータベース（NoSQL）

「Not Only SQL（SQLだけではない）」の略であり、RDBの表形式や厳格なルールの枠にとらわれない、新しいアーキテクチャのデータベースの総称である。

* **構造:** 用途に合わせて様々なデータモデルが存在する（ドキュメント型、キー・バリュー型、ワイドカラム型、グラフ型など）。
* **強み（高い拡張性と柔軟性）:**
    * **水平スケーラビリティ:** データを複数のサーバーに分散して保存（シャーディング）することが容易であり、ビッグデータや大量アクセスに強い。
    * **スキーマレス（柔軟性）:** 事前に厳格なデータ構造を定義する必要がなく、データの追加や仕様変更に柔軟に対応できる。
    * **高速な読み書き:** 単純なデータの取得や保存であれば、RDBのような結合処理（JOIN）が発生しないため、超高速で動作する。
* **弱み（課題）:**
    * データ間の一貫性（リアルタイムでの厳密な整合性）を担保することが難しい（結果整合性が基本となる）。
    * 複雑な条件での検索や集計処理には向いていない。
* **主要なプロダクト:** MongoDB（ドキュメント型）, Redis（キー・バリュー型）, Amazon DynamoDB

## 3. 比較表

| 項目 | リレーショナルデータベース (RDB) | 非リレーショナル (NoSQL) |
| :--- | :--- | :--- |
| **データ構造** | 構造化された「表（テーブル）」 | 自由な形式（JSON、キー・バリューなど） |
| **スキーマ定義** | 必須（事前の設計が必要。変更のハードルは高い） | 不要／柔軟（スキーマレス。変更が容易） |
| **整合性（一貫性）** | 極めて高い（ACID特性を厳格に遵守） | 結果整合性（多少の遅延や一時的な不整合を許容） |
| **拡張性（スケーリング）** | **垂直スケーリング（スケールアップ）**<br>サーバー単体のスペックを上げる | **水平スケーリング（スケールアウト）**<br>サーバーの台数を増やして分散する |
| **得意なユースケース** | 複雑な集計、厳密なトランザクション事務処理 | ビッグデータ、SNSのタイムライン、リアルタイム通信 |

## 4. 補足：RDBの根幹を支える「ACID特性」とは

RDBが「データの正確性」を保証できるのは、**ACID（アシッド）特性**と呼ばれる4つの厳格なルールを守っているからである。

* **Atomicity（原子性 / 不可分性）**
    * トランザクション（一連の処理）に含まれるタスクは、「すべて実行される」か「すべて実行されない（白紙に戻る）」の二者択一である。中途半端に一部だけが成功することはない。
    * *例: 振り込み処理で、引き落としだけ成功して入金が失敗した場合、処理全体がなかったことにされる。*
* **Consistency（一貫性 / 整合性）**
    * データベースのルール（制約）を満たした、矛盾のない状態を常に保ち続ける性質である。
    * *例: 「残高はマイナスになってはならない」というルールがあれば、マイナスになるような処理はエラーとなり実行されない。*
* **Isolation（分離性 / 独立性）**
    * 複数のトランザクションが同時に実行されても、それぞれの処理が互いに干渉しない性質である。並行して動いていても、順番に1つずつ実行されたのと同じ結果になる。
    * *例: Aさんが残高を確認している最中に、Bさんが同じ口座に振り込みを行っても、Aさんの処理が終わるまでBさんの変更は影響を与えない。*
* **Durability（永続性 / 持続性）**
    * 一度成功したトランザクションの結果は、その後システム障害（停電やクラッシュ）が発生しても、失われずにデータベースに残り続ける性質である。通常はログとしてディスクに書き込まれる。

## 5. 質問と回答

###  1. RDBとNoSQLの選定基準をどう考えていますか？

<details>
<summary>解答・解説を見る</summary>

**【解答例】**
    「データの性質」と「トラフィックの規模」の2軸で考える。
    データの正確性や複雑なリレーションが必要なシステム（ECの決済やユーザー管理など）であれば、迷わずRDBを選択する。
    一方で、リアルタイムなチャット機能のログ、SNSのいいね機能、あるいはIoTの大量のログデータなど、読み書きの速度とスケーラビリティ（拡張性）が最優先され、多少のデータ遅延が許容できるシステムであれば、NoSQL（RedisやDynamoDBなど）を選択する。

</details>

### 2. RDBとNoSQLの最大の違いを「データの持ち方」と「拡張性（スケーリング）」の観点から説明せよ。

<details>
<summary>解答・解説を見る</summary>

**【解答例】**
データの持ち方において、RDBは事前に定義された厳格な「表形式（テーブル）」で管理するのに対し、NoSQLはJSON（ドキュメント）やキー・バリューなど「自由な形式（スキーマレス）」で管理する。
拡張性において、RDBはサーバー単体の性能を上げる「垂直スケーリング（スケールアップ）」が基本だが、NoSQLは複数台のサーバーに分散する「水平スケーリング（スケールアウト）」が容易である。
</details>

---

### 3. RDBはなぜ複数台のサーバーに分散して処理（水平スケーリング）を行うことが構造上難しいのか、「ACID特性」という言葉を使って説明せよ。**

<details>
<summary>解答・解説を見る</summary>

**【解答例】**
RDBはデータの強力な「一貫性（Consistency）」や「分離性（Isolation）」といったACID特性を担保する構造だからである。
データを複数台のサーバーに分散すると、すべてのサーバー間で「同時に、確実に処理が成功したか」を同期・確認し合う通信（またはデータのロック制御）が発生する。大量の書き込みがある環境では、このネットワーク通信のオーバーヘッドが致命的なボトルネックとなるため、構造上スケーリングが難しい。

</details>
