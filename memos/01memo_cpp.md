> You may not use a using-directive to make all names from a namespace available.

- 名前空間を汚すので好まれない
- 原則としてコードはすべて名前空間に入れる
- インデントは下げない

- 外部に公開したくない、ライブラリ内部だけで使うクラスや関数は ...::internal または ...::internal_ファイル名 という名前空間にする

### 値渡しと参照渡し
const参照 `const auto& c` を型のサイズがレジスター幅以下の場合場合に用いると処理が遅くなる可能性がある。理由は、 const 参照で受け取ると、値を参照する際にアドレスの計算が 1 回入るため。普通に `auto c`とする。

### POD （Plain Old Data）
- POD:
    - Plain：仮想関数や継承などの、C++特有の複雑な仕組みが使われていない。
    - Old：C言語の時代からあるような。
    - Data：関数などの「動き」ではなく、ただのメモリ上の「値の並び」。
- POD の場合にデフォルト初期化を行うと適当なデータが入ったままの状態で初期化される。未定義動作。
- User-Provided Constructorsを定義している場合、デフォルト初期化が実行されたときはそちらが呼ばれる

### RVO (Return Value Optimization)
コンパイラが「最初から呼び出し元のメモリ領域に直接オブジェクトを構築することで、コピーもムーブも完全にゼロにする」最適化技術。
RVOには正確には2つの種類があり、コンパイラによる扱いが異なります。

- RVO（厳密にはURVO：Unnamed RVO）
    - return std::vector<int>{1, 2, 3}; のように、名前のない一時オブジェクトをそのまま返す場合。
    - C++17以降、規格で義務化されました。

- NRVO（Named RVO）
    - std::vector<int> v; ... return v; のように、名前のあるローカル変数を返す場合。
    - 強制ではなく、コンパイラの最適化任せです（ただ、現代の主要なコンパイラならほぼ確実にやってくれます）。
    - 複数のインスタンスのどれが戻されるか分からないときには行われない

RVOが効かない可能性を考慮してポインタ（または参照）で受け取る選択肢もある

> Return value optimization が多くの場合起きるので最適化されるとは思うが、されないこともあるので、ポインターへの書き込みの方が良い、などの定型的な発言は覚えておくといい

### 停止性判定
コンパイラが到達可能性を判定できない場合、途中で必ず return して終わるループなら到達しないことを明示的に無限ループで表すなどすると良いかも。

停止性問題: あるチューリングマシンが終了することを実行前に判定するアルゴリズムは存在しない（対角線論法）

### メモリリーク
C++にはGCがないためヒープの解法を忘れてはいけない。

https://qiita.com/seriru13/items/06d044cbe5bcc44cca10

```C++
ListNode* reverse_node = new ListNode();
```

メモリリーク（Memory Leak）：プログラムが使用するために確保したメモリ領域を、使い終わった後も解放（返却）し忘れてしまうことで、利用可能なメモリがどんどん減っていく現象

1. メモリリークの危険性: new を使って確保したメモリは、明示的に delete reverse_node; を呼ばない限り、プログラムが終了するまでメモリ上に残り続けます。もし解放を忘れたり、解放前にエラー（例外）が発生して関数を抜けてしまうと、メモリリークになります。

2. 生ポインタ（Raw Pointer）の管理負荷: 指摘されている通り、「読み手の負荷が高くなる（このポインタはどこで解放されるのか？を常に意識しなければならない）」という大きなデメリットが生じます。

3. ヒープが管理するためのオーバーヘッド（メタデータ）があるため、小さなオブジェクトを大量に new すると、本来のデータサイズ以上のメモリを消費する

4. スレッドセーフでない: 数のスレッドから同時に new や delete を行うと、ヒープ内部の管理領域が壊れる可能性があるため、内部でロック（同期処理）が走り、これがマルチスレッド性能のボトルネックになります。また、ポインタを再利用する性質上、並行プログラミングにおいてABA問題（一度削除されたメモリが再確保され、同じアドレスだから変化していないと誤認する問題）の引き金になります

#### 対策

1. スタックで済むならスタックで持つ
2. どうしてもヒープが必要なら「スマートポインタ」を使う。
```C++
#include <memory>

std::unique_ptr<ListNode> reverse_node = std::make_unique<ListNode>();
```

#### Heap(new演算子)を使うタイミング

- スコープから抜けた場合であっても破棄させない場合

ダメな例
```C++
int* createAnInteger() {
    int x = 10;
    return &x;
}
```

良い例
```C++
int* createAnInteger() {
    int* p = new int(10);
    return p;
}
```

- メモリを動的に確保したい場合

「動的に確保する」とは、プログラムを実行してみるまで、どれくらいのメモリ（サイズ）が必要か分からない状態でメモリを確保することです。

スタック領域はサイズが小さく（一般的に数MB程度）、コンパイルする時点で「何バイト使うか」が決まっていなければなりません。一方、ヒープ領域はPCの空きメモリ（数GB〜）を自由に使えるため、巨大なデータや、後からサイズが変わるデータに対応できます。

標準入力に応じてメモリを確保する場合など。
