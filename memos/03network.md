## 1. OSI参照モデルとトランスポート層

インターネットを流れるデータは、役割ごとに階層化されたプロトコル（約束事）に基づいて処理されている。これを概念化したものが**OSI参照モデル（7階層）**である。

### OSI参照モデルの全体像
Web開発に直結するのは「アプリケーション層（L7）」「トランスポート層（L4）」。

* **第7層：アプリケーション層 (L7)**
    * ユーザーが操作するソフトウェア（ブラウザなど）が直接利用する層。
    * *プロトコル例:* HTTP, HTTPS, SSH, SMTP
* **第6層：プレゼンテーション層 (L6)**
    * データの表現形式（文字コード、暗号化、圧縮など）を定義する層。
* **第5層：セッション層 (L5)**
    * 通信の開始から終了までの「一連の会話（セッション）」を管理する層。
* **第4層：トランスポート層 (L4)**
    * データを目的のアプリケーションまで**「どう届けるか（通信の信頼性）」**を制御する層。
    * *プロトコル例:* TCP, UDP
* **第3層：ネットワーク層 (L3)**
    * ルーターなどを経由し、目的のIPアドレスまでデータを届ける（ルーティング）層。
    * *プロトコル例:* IP
* **第2層：データリンク層 (L2)**
    * 同じネットワーク内（LAN内）の隣り合う機器同士の通信を制御する層。
    * *プロトコル例:* イーサネット, MACアドレス
* **第1層：物理層 (L1)**
    * データを電気信号や光信号に変換し、物理的なケーブルで送信する層。

---

### トランスポート層の主役：TCP と UDP の違い

両者の最大の違いは**「信頼性を重視するか、速度を重視するか」**にある。

| 項目 | TCP (Transmission Control Protocol) | UDP (User Datagram Protocol) |
| :--- | :--- | :--- |
| **通信方式** | コネクション型（接続を確認してから通信） | コネクションレス型（一方的に送りつける） |
| **信頼性** | **極めて高い**（エラー検知、再送制御あり） | **低い**（送りっぱなしで確認しない） |
| **速度** | 遅い（確認の手間がかかるため） | **速い**（オーバーヘッドがないため） |
| **主な用途** | Webページ（HTTP）、メール、ファイル転送 | 動画配信、オンラインゲーム、音声通話 |

#### パケットロスとその影響
データは細切れの「パケット」という単位で送られるが、ネットワークの混雑などが原因で途中で消失することがある。これを**パケットロス**と呼ぶ。
* **TCPの場合:** パケットロスを検知すると、送信側に「再送リクエスト」を送り、データを正しく復元する。そのためデータは欠損しないが、再送の分だけ通信に遅延が発生する。
* **UDPの場合:** パケットロスが発生しても無視して次のデータを送り続ける。動画が一時的にモザイク状になったり音声が一瞬途切れたりするのは、このパケットロスが原因である。

## 2. セキュリティの標準：HTTPS

**HTTPS（Hypertext Transfer Protocol Secure）**は、HTTP通信を暗号化プロトコル（**SSL/TLS**）で保護したものである。

* **目的:** 「盗聴（データの覗き見）」「改ざん（データの書き換え）」「なりすまし（偽サイト）」を防止する。
* **仕組み:** 従来のHTTP（ポート番号80）のデータを、L4とL7の間でTLSによって暗号化してから送信する（ポート番号443）。
* 「HTTPSはHTTPとは全く異なる新しいプロトコルである」は誤りである。**「HTTPのメッセージ内容を、SSL/TLSという仕組みを使って暗号化して流している通信」**が正確である。

## 3. HTTPリクエスト：GET と POST の違い

ブラウザからサーバーへデータを送る際、最も多用される2つのメソッド（形式）である。面接では「どのようにデータを送るか」の構造の違いが問われる。

### GETメソッド
* **用途:** サーバーから情報を**「取得」**するために使用する。
* **データの送り方:** データをURLの末尾に付与する（**クエリストリング / URLパラメータ**）。
    * *例:* `https://example.com/search?q=keyword`
* **特徴:** URLにデータが露出するため、パスワードなどの機密情報の送信には適さない。また、URLの長さに上限がある。ブラウザにキャッシュされやすい。

### POSTメソッド
* **用途:** サーバーへ新たなデータを**「送信・作成」**するために使用する。
* **データの送り方:** データをURLではなく、HTTPリクエストの**「メッセージボディ（リクエストボディ）」**に格納して送信する。
* **特徴:** URLにデータが表示されないため、GETよりも大量かつ安全にデータ（個人情報や画像ファイルなど）を送信できる。

## 4. HTTPメッセージの構造（ヘッダーとボディ）

HTTPの通信（リクエスト/レスポンス）は、大きく**「ヘッダー」**と**「ボディ」**の2つのセクションで構成されている。
※歴史的な経緯や仕様上、データの末尾を示す概念を「フッター（トレイラー）」と呼ぶこともあるが、主要なメタ情報はすべて「ヘッダー」に含まれる。

### HTTPレスポンスの構造

1. **ステータスライン:** プロトコルバージョンとステータスコード（例: `HTTP/1.1 200 OK`）
2. **レスポンスヘッダー:** メッセージのメタ情報（データの形式やサイズ、サーバー情報など）
3. **空行:** ヘッダーとボディの境界を示す重要な改行
4. **レスポンスボディ:** 送るデータそのもの（HTML、JSON、画像データなど）

---

### 重要なHTTPヘッダー一覧

基本ヘッダー

* **Content-Type（コンテントタイプ）**
    * ボディに含まれるデータの種類（メディアタイプ）を相手に伝える。
    * *例1（JSONで送る場合）:* `Content-Type: application/json`
    * *例2（HTMLの場合）:* `Content-Type: text/html; charset=utf-8`
    * *例3（フォーム送信の場合）:* `Content-Type: application/x-www-form-urlencoded`
* **Accept（アクセプト）**
    * クライアント（ブラウザ）側からサーバーに対し、「自分はどのデータ形式（MIMEタイプ）を受け付けられるか」を伝えるリクエストヘッダーである。
    * *例:* `Accept: application/json` （JSON形式で返してほしい、という要求）
* **Content-Encoding（コンテントエンコーディング）**
    * データの圧縮方式を示す。サーバーがデータを圧縮して送り、クライアントがそれを解凍する。
    * *例:* `Content-Encoding: gzip` や `br`（Brotli）

## 5. HTTPステータスコード

サーバーからの返答（レスポンス）の状態を表す3桁の数字である。百の位ごとに分類を覚えておく必要がある。

* **2xx (Success) : 成功**
    * `200 OK`: リクエストが正常に成功した。
    * `201 Created`: リクエストが成功し、新しいリソースが作成された（POSTリクエストの成功時など）。
* **3xx (Redirection) : 転送**
    * `301 Moved Permanently`: 該当URLが恒久的に移動した（自動的に新URLへリダイレクトされる）。
    * `304 Not Modified`: キャッシュが有効であるため、再ダウンロードの必要がないことを示す。
* **4xx (Client Error) : クライアント側のエラー**
    * `400 Bad Request`: リクエストの構文が正しくない（開発時のパラメータミスなど）。
    * `401 Unauthorized`: 認証が必要である、または認証に失敗した。
    * `403 Forbidden`: アクセス権限がない（閲覧禁止）。
    * `404 Not Found`: 指定されたリソース（URL）が存在しない。
* **5xx (Server Error) : サーバー側のエラー**
    * `500 Internal Server Error`: サーバー内部で予期せぬエラー（プログラムのバグなど）が発生した。
    * `503 Service Unavailable`: サーバーが過負荷、またはメンテナンス中で一時的にアクセスできない。

## 6. 実践想定クイズ

### 問1
**Q. API通信でフロントエンドからバックエンドへユーザー情報を「JSON形式」で送信したい場合、HTTPリクエストのどの部分に、どのようなヘッダーを設定すべきか説明せよ。**

<details>
<summary>解答・解説を見る</summary>

**【解答例】**
データを送信するため、HTTPメソッドには**POST**（またはPUT/PATCH）を使用し、ユーザー情報となるJSONデータはURLではなく**「リクエストボディ（メッセージボディ）」**に格納する。
また、サーバー側に「このデータはJSONである」と正しく認識させるため、リクエストヘッダーの **`Content-Type` に `application/json`** を設定する必要がある。
</details>

### 問2
**Q. あなたが開発したWebサイトで、画面に「500 Internal Server Error」が表示された。この時、原因はクライアント（ブラウザ側）とサーバー側のどちらにあるか。また、最初に行うべき調査は何か。**

<details>
<summary>解答・解説を見る</summary>

**【解答例】**
5xx系のステータスコードは「サーバー側のエラー」であるため、原因はサーバー側のプログラムやインフラにある。
最初に行うべき調査は、**サーバーのアプリケーションログやエラーログの確認**である。プログラム内で例外（例外処理されていないバグ）が発生していないか、データベースへの接続に失敗していないかなどをログから特定する。クライアント側のJavaScriptやリクエスト内容の修正ではなく、サーバーサイドのコードや状態を確認するアプローチが正しい。
</details>
